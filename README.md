# Express + Passport Auth Server

Сервер на Node.js/Express з авторизацією через **Passport** (локальна стратегія email/пароль), збереженням сесій через `express-session`, захищеним маршрутом `/protected`, заготовкою під OAuth (Google) та функціональністю відновлення забутого пароля через електронну пошту.

Усі вихідні файли проєкту знаходяться в директорії `src/`; у корені залишені лише конфігураційні/проєктні файли (`package.json`, `.env.example`, `.gitignore`, `README.md`).

## Структура проєкту

```
.
├── package.json
├── .env.example
├── .gitignore
├── README.md
└── src/
    ├── server.js                  # Точка входу: завантажує .env і запускає сервер
    ├── app.js                     # Збірка Express-застосунку: middleware, сесії, passport, маршрути
    ├── config/
    │   ├── session.js             # Налаштування express-session (httpOnly, secure, cookie)
    │   └── passport.js            # Стратегії Passport: local + Google OAuth2, serialize/deserialize
    ├── controllers/
    │   └── authController.js      # Логіка register/login/logout/forgot-password/reset-password
    ├── middlewares/
    │   └── ensureAuthenticated.js # Мідлвар перевірки валідної сесії перед доступом до /protected
    ├── models/
    │   └── User.js                # In-memory сховище користувачів (bcrypt-хешування, reset-токени)
    ├── routes/
    │   ├── auth.js                # /auth/* маршрути
    │   └── protected.js           # /protected маршрут
    └── utils/
        └── mailer.js              # Надсилання email для відновлення пароля (nodemailer)
```

> **Примітка щодо зберігання даних:** для простоти запуску "з коробки" користувачі зберігаються в пам'яті процесу (`src/models/User.js`). Для продакшн-використання замініть реалізацію `UserStore` на звернення до реальної БД (MongoDB/PostgreSQL тощо), зберігши ті самі методи (`create`, `findByEmail`, `findById`, `setResetToken`, ...), — решта застосунку зміниться мінімально. Так само `express-session` використовує стандартний `MemoryStore`, придатний лише для розробки; для продакшну підключіть персистентне сховище сесій (наприклад `connect-redis`, `connect-mongo`).

## Встановлення та запуск

### Вимоги
- Node.js >= 18
- npm

### Кроки

1. Встановити залежності:
   ```bash
   npm install
   ```

2. Створити файл `.env` на основі прикладу та за потреби відредагувати значення:
   ```bash
   cp .env.example .env
   ```

   Ключові змінні:
   | Змінна | Опис |
   |---|---|
   | `PORT` | Порт, на якому запускається сервер (за замовчуванням `3000`) |
   | `SESSION_SECRET` | Секрет для підпису cookie сесії — обов'язково змінити в продакшні |
   | `USE_SECURE_COOKIES` | `true`, якщо застосунок працює за HTTPS (додає прапорець `secure` до cookie сесії) |
   | `RESET_TOKEN_TTL_MINUTES` | Термін дії токена відновлення пароля в хвилинах |
   | `APP_BASE_URL` | Базовий URL, що використовується для формування посилання відновлення пароля |
   | `SMTP_*`, `MAIL_FROM` | Налаштування SMTP для надсилання email. Якщо не задані — лист просто виводиться в консоль (зручно для локальної розробки/тестування) |
   | `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GOOGLE_CALLBACK_URL` | Опційні — якщо задані, активується стратегія Google OAuth2 |

3. Запустити сервер:
   ```bash
   npm start
   ```
   або в режимі розробки з автоперезапуском (`nodemon`):
   ```bash
   npm run dev
   ```

4. Сервер буде доступний за адресою `http://localhost:3000`.

## Опис маршрутів

Усі маршрути (окрім зазначеного) приймають/повертають `application/json`.

### `GET /`
Коротка довідка про сервер та список доступних маршрутів.

### `POST /auth/register`
Реєстрація нового користувача.

- **Тіло запиту:**
  ```json
  { "email": "user@example.com", "password": "secret123", "displayName": "Ім'я (опційно)" }
  ```
- **Поведінка:** хешує пароль через bcrypt, створює користувача, одразу автоматично авторизує (`req.login`) і створює сесію.
- **Відповіді:** `201` з об'єктом користувача; `409` якщо email вже зайнято; `400` при відсутніх/некоректних полях.

### `POST /auth/login`
Вхід через стратегію Passport `local`.

- **Тіло запиту:**
  ```json
  { "email": "user@example.com", "password": "secret123" }
  ```
- **Поведінка:** Passport перевіряє email/пароль; за успіху створюється сесія, а ідентифікатор сесії зберігається у cookie `sid` (`httpOnly`, за потреби `secure`).
- **Відповіді:** `200` з об'єктом користувача; `401` при невірних облікових даних.

### `POST /auth/logout`
Завершення сесії поточного користувача (`req.logout`) та її знищення на сервері, з очищенням cookie `sid`.

- **Відповідь:** `200` з повідомленням про успішний вихід.

### `GET /auth/me`
Повертає поточного авторизованого користувача (або `null`, якщо сесія відсутня/невалідна). Зручно для перевірки стану авторизації на фронтенді.

### `POST /auth/forgot-password`
Запит на відновлення пароля.

- **Тіло запиту:** `{ "email": "user@example.com" }`
- **Поведінка:** якщо користувача з таким email знайдено — генерується одноразовий токен (зберігається лише його хеш, з терміном дії `RESET_TOKEN_TTL_MINUTES`), і на пошту надсилається лист з посиланням виду `APP_BASE_URL/auth/reset-password?token=...`. Відповідь однакова незалежно від того, існує email чи ні — це запобігає розкриттю списку зареєстрованих email.

### `POST /auth/reset-password`
Встановлення нового пароля за токеном з листа.

- **Тіло запиту:** `{ "token": "...", "password": "newSecret123" }`
- **Поведінка:** перевіряє токен (хеш і термін дії), встановлює новий пароль, інвалідовує токен.
- **Відповіді:** `200` при успіху; `400` якщо токен недійсний/прострочений або пароль закороткий.

### `GET /auth/google`
Ініціює вхід через Google OAuth2 (активний лише якщо в `.env` задані `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`). Перенаправляє користувача на сторінку згоди Google.

### `GET /auth/google/callback`
Callback-маршрут, на який Google повертає користувача після авторизації. При успіху створюється (або знаходиться наявний) локальний обліковий запис за email з профілю Google, створюється сесія, і користувач перенаправляється на `/protected`. При невдачі — редірект на `/auth/google/failure`.

### `GET /protected`
Захищений маршрут. Доступ надається лише за наявності валідної авторизованої сесії — це перевіряє мідлвар `ensureAuthenticated` (використовує `req.isAuthenticated()` від Passport) до виконання обробника маршруту.

- **Відповіді:** `200` з даними користувача, якщо сесія валідна; `401`, якщо користувач не авторизований.

## Приклад сценарію роботи (curl)

```bash
# Реєстрація (зберігає cookie сесії у файл cookies.txt)
curl -c cookies.txt -X POST http://localhost:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"secret123"}'

# Доступ до захищеного маршруту з тією ж сесією
curl -b cookies.txt http://localhost:3000/protected

# Вихід
curl -b cookies.txt -X POST http://localhost:3000/auth/logout
```

## Безпека сесій

- Cookie сесії (`sid`) встановлюється з прапорцем `httpOnly`, що унеможливлює доступ до неї з клієнтського JavaScript.
- Прапорець `secure` вмикається через `USE_SECURE_COOKIES=true` — застосовуйте це в продакшні за HTTPS, щоб cookie передавалася лише захищеним з'єднанням.
- `sameSite: 'lax'` додає базовий захист від CSRF для типового сценарію автентифікації на основі сесій.

## Подальший розвиток

- Підключення додаткових стратегій Passport (Facebook, GitHub тощо) — за тим самим патерном, що й `GoogleStrategy` у `src/config/passport.js`.
- Заміна in-memory `UserStore` та `MemoryStore` сесій на персистентні рішення (БД, Redis) для продакшн-розгортання.
- Додавання валідації вхідних даних (наприклад, через `zod`/`joi`) та rate-limiting на маршрутах `/auth/login` і `/auth/forgot-password`.
